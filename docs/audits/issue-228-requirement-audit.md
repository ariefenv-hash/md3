## ② 语义检查 —— 比正文要求多出四套并行段

正文只要求「计数 → 语义」的四条（range 命中组件 / 760px 有实质差异 / 按行数比例 / SDK 真调用）。实树落地为：

| 段 | 项数 | 硬阻断 |

| **J 触控命中区**（#294） | 1 | 报告级 |
| **K 巨石阈值**（#284） | 1 | 违规拦截 |
| **O vendor 孤儿**（#280） | 1 | 孤儿拦截 |

语义判据逐条坐实（读引擎源码 + 分项 `detail`）：

- **A**：`var(--md-) ≥ 15` **且** 密度 `≥ 4 处/100 行` → 大文件只引 12 处不再能蒙混
- **B**：`@media ≥ 1` **且** `min-width:760px ≥ 1` **且该块内有实质布局差异**（`grid-template-columns` / `flex-direction` / `display:none`），空媒体查询不算
- **C**：`__system` 真实调用 ≥ 1，**剥注释后匹配**（注释命中不算）
- **D**：每个 `type="range"` 命中 `.mdslider` 且应用内**零自定义** `::-webkit-slider-thumb` / `::-moz-range-thumb` / 轨道伪元素 —— 任何阶段硬 fail
- **E–I**：无障碍锚、动效锚+曲线令牌化、持久化、tests 引用应用 id、状态层/形状/字体令牌
- **基线回退守卫**：`scripts/quality-baseline.json`（6666 B，按应用 id 顶层键）记录开卡时通过项，**曾经达标掉线即 fail**，任何阶段硬 fail —— 保证原 17 应用白名单的门禁强度在全量化后不变弱

模板同审（`app-template-multi` 三件套 + `app-template.html`）走同一评分卡，**不占 N 计数**。

## ⑤ 假应用回归断言 —— 唯一与正文有口径差的一项

按正文要求⑤造一个 `__probe_zero__/index.html`（零令牌、零断点），三个 phase 各跑一次：

| phase | `checked` | `hardFailures` | 日志是否曝光假应用 |
| --- | --- | --- | --- |
| **1（当前默认）** | 42 | **0** | ✅ 3 处（`严重: __probe_zero__`、`缺 V1/V2/V3/V4` …） |
| 2 | 42 | **1** | ✅ `[阶段2] 严重档 __probe_zero__(0/9) 缺 A,B,C,D,E,F,G,H,I` |
| 3 | 42 | **7** | ✅ 假应用 + 6 个偏薄应用一起 fail |

→ **正文「故意新建一个 `--md-*=0` 的假应用，构建必须 fail」在阶段 1 不成立**：新应用不在基线内，由分期管，只 warn 曝光、不阻断。这是 #230 §四「防一刀切全红」的刻意制度设计，**不是缺陷**。

**但 `vite.config.js:258` 把 `phase` 固定为 1**，所以当前构建默认**不会因新应用整体过薄而 fail**。两类不受分期豁免的防线仍然生效：**D 滑块单源门禁** 与 **基线回退门禁**。

### ⚠️ 留给用户的裁决项（本侧不擅自改）

若要求⑤按字面完全兑现，需把默认 phase 提到 2 或 3。但实测 phase3 会立刻产生 **7 条硬失败**（假应用 + 6 个偏薄存量应用），`Run vitest` 前的门禁会让部署全跳过 —— 正是 #235 连红复发过的形态。所以合理路径是二选一：

- **A**：保持 phase 1，把要求⑤改写为「warn 曝光 + 基线/滑块硬 fail」，承认分期口径（当前实树即此形态）
- **B**：先清完 6 个偏薄应用（补齐 B/C/D），再切 phase 2 → 3

这一步属**制度裁决权**，本侧只给数据，不动 `vite.config.js`。
