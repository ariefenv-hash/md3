# 定时任务产出瘦身纪律（#80 · v8.35 落地）

> 执行侧（会话代理）与机器工作流共用的一页纪律。机制实现见 `.github/cockpit.sh`，
> 行为级守护见 `tests/v835-ops-cockpit.test.js`。

## 一、驾驶舱机制（机器侧，已自动化）

- 「每日简报」议题（#17）恒为 **1 条**机器评论（`<!-- cockpit -->` 标记），
  `daily-issue-brief`（每日 01:00）与 `issue-patrol`（每 6 小时）共用同一条，原地 PATCH。
- **指纹 diff**：指纹 = 开放议题号集合（排除跟踪议题自身）+ vitest 门禁态，
  存于隐藏块 `<!-- fp:... -->` 与 `<!-- state:... -->`。
  排除跟踪议题自身（每次 PATCH 都会 bump 其 updatedAt，计入则永无静默轮）；
  仅用议题号集合（评论/编辑活动不改开合事件集，无事件 = 静默）。
- **静默轮**：指纹不变 → 仅刷新时间戳与摘要行，变更区写「本轮无变化」，
  24h 滚动日志逐字保留（连续两轮无变化不重写变更区）。
- **事件轮**：开/关/门禁翻转事件前置进 24h 滚动日志（≤20 条，仅留 24h 内条目）；
  vitest 失败仅在翻转轮附尾部日志。
- **全量盘点不进评论**：摘要一行 + 变更区，明细按需 `gh issue list` 现查。
- **首启迁移**：无 cockpit 评论时收编最旧机器评论（`<!-- patrol-snapshot -->` 或
  旧版「## 每日简报」）PATCH 成驾驶舱，并清扫其余机器评论
  （作者=github-actions[bot] 且带机器标记双守卫，人工评论绝不触碰）——
  #17 评论总数收敛为「驾驶舱×1 + 人工评论」。

## 二、落地侧产出纪律（执行侧，即每轮会话代理）

| 场景 | 做法 |
|---|---|
| 正常完成一个议题 | 该议题内留**一行**：`已完成 · v8.xx · <commit sha 前 7 位>`，然后 close。**不新开报告、不在 #17 刷屏** |
| 一个议题跨多轮执行 | 同一条 `<!-- wip -->` 评论**原地 PATCH** 更新进度，不逐次追加 |
| 遇到阻塞 | 在议题内开一条**详细**评论说明卡点（唯一允许长篇的情况） |
| 提交粒度 | 单个议题内多轮提交 **squash** 为一个「vX.XX: #NN 主题」提交，不把 3 小时中间态拆成十几个 commit |
| 巡查发现（池空后） | 按 #77：发现即开独立议题挂回对应里程碑，本轮日志只在 #77 追加一条（同样原地更新 + diff） |

- 提交消息格式：`vX.XX: #NN <主题>`——从议题号可反查，无需重复写长描述。
- 提交频次本身反映真实工作量，**不需要压低**；要压的是**报告频次**，两者勿混。
- 上下文交接锚点：#18。本机制作为模板被 #77 继承（池空期巡查日志同样原地更新 + diff）。

## 三、验证锚点（#80 DoD 抽查法）

- #17 机器评论恒 1 条（cockpit 标记）；issue-patrol 不再独立写快照。
- 连续两轮无变化时，第二轮不重写变更区，仅更新时间戳并标注「本轮无变化」。
- 门禁结果仅在状态翻转（✅↔❌）时进变更区；持续通过时只在摘要行显示。
- 落地侧完成议题后，#17 零新增评论（抽查）。
- 单议题跨多轮时进度写在同一条 WIP 评论内（抽查未逐轮追加）。
- 周期复盘：#17 评论总数 ≤ 3 条（驾驶舱 + 2 条人工评论）。

## 四、「注释 = 代码」强制核对纪律（#149 · v8.97 落地）

> 背景：#149 系统性审计实证 6 处「注释写了权威考证结论，代码没跟着落地」
> （4 处集中在文件头注释）。危害高于「没写注释」：后来者照着注释信，不再核验
> （#135 设置图标 40dp 注释 vs 34px 代码长期无人发现是活例）。

### 1. 机器核对（CI 门禁）

- `scripts/check-comment-claims.mjs`：扫描注释中的数值声明
  （dp / px / ms / 「N 组、态、项、维」），同文件代码区检索不到该数值即失配候选。
- 基线豁免表 `scripts/comment-claims-allowlist.json`（file + token 粒度，**每条必须
  写 reason**）：叙述性引用（AOSP 源值原文 / 量纲映射 / 几何核算结论）经人工复核后
  豁免；CI 只对**新增失配**报错，豁免表不允许 `--update` 自动刷新入 CI。
- 处置顺序（新失配时）：① 先怀疑注释失血 → 修注释或代码使之一致；
  ② 确认属叙述性引用 → 入豁免表并写明 reason。**禁止无 reason 入表。**

### 2. 数量声明必须配断言（测试兜底）

- 头注释声明的「N 态 / N 组 / N 项 / N 个应用」必须在 tests/ 有同款数量断言
  （范例：`tests/v840-terminal.test.js` 断言 `APPS.length === 45`；
  `tests/v821-back-pill.test.js` ① 逐条断言 DIMS 六态全量键值）。
- 数量声明 + 断言双缺 → 注释失血时无人兜底（#149 第 6 条教训）。

### 3. 评审清单（新增移植 PR 必答）

- [ ] 头注释里声称的每一条，是否都能在代码里指出来？
- [ ] 注释中的每个数值（dp/px/ms/弹簧参数/组数），`check-comment-claims` 是否零失配？
- [ ] 数量声明是否已配 tests/ 数量断言？

### 4. 同源防线：dist 产物完整性（#138/#139）

- `scripts/verify-dist.mjs`（构建后）：应用目录平行 / 引用闭合 / precache 双向自洽。
- `scripts/e2e-dist-smoke.mjs`（部署前）：dist 档全应用浏览器冒烟（iframe 挂载 +
  非空 + 无错误文案 + 零 pageerror）+ precache 清单逐 URL HTTP 自校验。
- 教训：e2e 只跑源码档时，「源码有、dist 没有」100% 测不出——两档必须并存。
