## 二、逐条实证与验收口径草案

### P1 音量键捕获无反应 → 并入 #106

- **现树实证**：`ios-desktop/js/volume-dialog.js` L849/L854 的 `keydown`/`keyup` 监听仍挂**父 window**；无任何焦点桥处理（该文件 grep `blur|focus` 零命中）。浏览器语义：键盘事件不跨 document 冒泡，焦点一旦进入子应用 iframe，父 window 收不到音量键——与 #106 正文实证的机理逐字一致。
- **边界澄清**：`ios-desktop/js/aosp/key-dispatcher.js`（#111 组合键路由，v9.94 落地，159 行纯逻辑零 DOM）已被 volume-dialog.js 消费做组合键检测，但它**不是** #106 要的全局按键派发层——没有 iframe 焦点桥，音量键在应用内依旧丢。
- **验收口径草案（并入 #106 后作其首条）**：子应用 iframe 聚焦状态下按音量上/下，音量步进且 volume-dialog 弹出；桌面态不回归。
- **移动端注记**：移动浏览器对 `AudioVolumeUp/Down` key 的派发因浏览器而异（物理音量键多数由系统消费，网页收不到）——#106 正文已含 opaque origin iframe 方向；本条复现条件应以「应用内使用键盘导航 / 外接键盘 / 模拟按键」为准，真机物理键可行性边界在立卡时写明，不夸口。

### P2 音量完全展开菜单缺失 → 新点候选

- **现树实证**：`volume-dialog.js` L905 注释自曝：「省略号：打开系统设置（真机 = 展开完整音量面板，网页以 Settings App 声音区承接）」——**展开态被委托给设置应用**，未实现 AOSP `VolumeDialogImpl` 的 expanded 多滑条面板。
- **AOSP 差距**：真机点击省略号后为完整音量面板（media / 蓝牙 / 铃声等多通道滑条 + 设置入口），现树只有单滑条 + 铃声抽屉（L286/L884）。
- **复现条件**：音量键/滑条唤起 volume-dialog → 点省略号 → 观察是否跳设置应用而非就地展开。
- **验收口径草案**：省略号就地展开完整面板，≥2 通道滑条同屏，通道取值与 #10 声音区五通道真源一致。
- **依赖注记**：声音五通道语义已在设置声音区落地（#10 一期），本卡是消费方侧的展示面，不重做真源。

### P3 新应用设计不达标 → 并入 #228

- **重合**：#228（P0·open）正文即「新建应用仍过简洁」的制度性根因（准入 lint 17 应用硬编码白名单、24 应用完全绕过、41 应用实测扫描表）；本条用户反馈是 #228 立项后**第三次同类问题的用户侧再实证**（#175/#179/#18 §2.1 之后仍复现）。
- **处置**：并入 #228 评论区作用户反馈引证，不新开卡；§2.1⑥（脚手架模板先达标）与 #227（怠速柄 6 种规格）继续作为 #228 的配套面。

### P4 后台卡片白底 → 新点候选

- **现树实证**：`recent-apps.js` L777、`recent-preview.js` L23/L101/L143/L152/L166 的卡片与预览底均为 `var(--md-surface,#121418)` 实色/渐变——**卡片底本身不是白**。白底疑似出在「能显示壁纸的应用」的**预览快照链**：快照未捕获到壁纸层/透明层时回退成浅色或空底。
- **待复现**：需在无头环境列出「哪些应用显示壁纸」（桌面壳/壁纸映射类）、逐个退后台看快照，定位是快照截取时机（壁纸未渲染）还是背景兜底色不当。
- **验收口径草案**：任意应用退后台，后台卡片底色与应用真实首屏一致；壁纸应用卡片可见壁纸，不再出现白底。
- **与既有议题边界**：#225 是开窗动画 44×44 卡死、#247 是快速切换标题错位——症状不同，不重合。

### P5 应用主题色令牌闪烁 → 新点候选（首次补登）

- **用户定性**：「老问题」，此前零议题零登记——本次为首次补登，避免再丢。
- **现树锚点**：主题令牌注入链在 `theme-engine.js` / `iframe-app.js`（grep `setProperty('--md-` 命中）；开窗动画与令牌到达的时序差是闪烁的直接嫌疑面。
- **待取证**：开窗全链路逐帧录（无头 Chromium，`launchOpacity` 链路）确认闪烁帧发生在令牌注入前还是字体/壁纸解码期；两因修法不同（前者改注入时序，后者属解码占位）。
- **验收口径草案**：开窗全程逐帧无可见令牌跳变（底色/前景色一次性到位）。

### P6 控制中心展开应显更多磁贴 → 代码已实现，待实测复核

- **现树实证**：`quick-settings.js` 已有 AOSP 同构双层结构——L669「统一 Shade 双容器：QQS（#qqsTilesContainer 前 4 大磁贴）+ QS 全量网格」；L397-409 `distributeTiles` 分页（PagedTileLayout L399-411 同构，「满页即封、溢出进下页」）。**代码层「展开显更多 + 分页」已落地。**
- **待复核**：用户在 v11.22 线上版实测仍觉得展开没有更多磁贴，两种可能：(a) 展开手势/过渡有回归，QQS→QS 切换未生效；(b) 用户对「更多」的预期与现分页实现不一致（页数少/磁贴总量少）。需无头实测展开全程（QQS 4 → QS 全量网格页数、磁贴数逐帧计数）后回复实证结论；若复现 (a) 则立回归卡。
- **验收口径草案（若立回归卡）**：收起态 4 大磁贴，任一展开路径（下拉/点击）后磁贴数量与分页数与 #34 磁贴清单一致，过渡无跳变。

### P7 取向条款：可连外部资源，别手搓 → 条款

### P8 图标扩散/收回开关 → 部分已覆盖，差一个「关闭」档

- **现树实证**：`apps/settings.js` L2485「选择应用从图标展开 / 收回时的弹簧手感」设置已存在，含样式切换（L2531「Android 涟漪扩散」/ iOS 液态玻璃 / macOS 吸入融合，切换即时生效并持久保存）。
- **差距点**：现开关只有**样式选择**，没有**关闭该效果**的档位——用户要的是「有相对应的开关」（可关）。
- **建议处置**：小卡候选（动画样式组增加「关闭/直接打开」档）；改动面小，可与 P5/P12 同卷或作轻量加餐。
- **验收口径草案**：选择「关闭」后开窗无图标扩散/收回动画（直接呈现），其余样式不回归。

### P9 状态栏重叠 → 新点候选

- **症状**：控制中心展开 / 合体模式下快速滑动，状态栏「重叠两次」（观感为两层状态栏叠影）。
- **现树锚点**：`ios-desktop/js/status-bar.js`（变换链）+ Shade 拖拽链（quick-settings.js）；嫌疑面为快速手势下 shade 位移与状态栏 transform 的竞态或双实例叠加。
- **待复现**：无头模拟快速拖拽 CC（高于人类手速的 pointer 序列）逐帧截帧定位重叠帧；真机指感不可自动化，以帧序列为准。
- **验收口径草案**：任意拖拽速率下状态栏单实例可见，无叠影帧。

### P10 分屏二级菜单上浮阴影 → 待考证

- **症状**：文件应用在分屏模式下打开二级菜单出现上浮层阴影，用户质疑「这是为什么」。
- **现树锚点**：分屏实现在 `ios-desktop/js/split-screen.js`（grep shadow/二级零命中——阴影大概率来自应用内 context-menu 组件的 elevation 样式，需进 `apps/files` 实查）。
- **考证路线**：先取 MD3/AOSP 弹出菜单 elevation 规范（menu elevation = 3dp 阴影属规范内），再判定分屏场景是否误用了更高 elevation 或多余阴影层；若属规范内则回复用户「这是规范行为」并给出处，若属实现偏差则立卡修。
- **验收口径草案（若立卡）**：分屏内外二级菜单阴影规格统一，与规范取值一致。

### P11 开关小球难看见 → 待澄清（两种读法）

- **读法 A（开关 thumb）**：设置/QS 开关的小球在按压放大时#79 已修过「偏上/留缝」（closed）；「慢滑也一闪而过」与开关无滑动语义不符，读法 A 存疑。
- **读法 B（滑条怠速柄）**：`apps/_shared/idle-slider.css` L63/L92 柄宽 0.2s 过渡 + L102 轨道 opacity 0.38——若用户指的是亮度/音量滑条的怠速柄，则「滑动很慢柄很快消失」指向**消隐时序过短**（交互中柄被 idle 判定收走），与 #227（怠速柄全库 6 种规格统一）有交叉面。
- **需用户补一句**：出现位置是「设置里的开关」还是「亮度/音量滑条」？确认后立卡，验收口径按读法定（A=thumb 全程可见性，B=交互中柄不消隐 + 消隐时长对齐规范）。

### P12 应用内壁纸映射可读性 → 新点候选（用户已给方案）

- **用户方案**：应用内不再直接映射壁纸，**取壁纸主题色作为底板颜色**——即 Material You 动态色方向（wallpaper → palette → surface tint）。
- **现树基建**：`theme-engine.js` / `wallpaper.js` / `video-wallpaper.js` 已有 `setProperty('--md-*`)` 动态注入链，动态色基建存在；缺的是「壁纸→主色提取→底板令牌」的消费段。
- **建议处置**：中型卡候选；与 P5（令牌闪烁）同属主题令牌链路，**建议同卷设计**（一次把注入时序与壁纸取色底板定稿，避免两次动同一链路）。
- **验收口径草案**：应用底板取壁纸主题色（可读性达标：底板与前景对比度 ≥ WCAG AA），主题切换/壁纸更换联动，静态壁纸与视频壁纸两源一致。

### P13 权限申请窗口移到右侧 → 新点候选

- **现树锚点**：授权对话框内容真身 `ios-desktop/js/aosp/grant-permissions.js`；窗体落位由窗管/宿主层决定（内容文件 grep 定位样式零命中）。
- **待复现**：触发任一权限申请（如定位应用首启），记录窗口落位；对照 AOSP 授权对话框应居中/居下（AOSP GrantPermissionsActivity 窗口居中），定位归因是窗管定位逻辑还是对话框样式。
- **验收口径草案**：权限申请窗口落位与 AOSP 一致（居中），不随双栏/右侧布局漂移。
- **与 P14 关联**：若 P14 裁决为「双栏滥用需收敛」，本条大概率是同一根因的实例，可并卷。

### P14 双栏滥用 → 制度张力，需用户裁决

- **张力本质**：#18 §2.1③ 把「平板态须分栏」定为**硬门禁**（对齐设置 tp-wide 范式），新应用准入必须分栏——而用户本条明确「双栏本意是提升平板显示效率，却被强行改成非常不合适的双栏」。准则本身可能就是滥用推手：为过门禁而分栏。
- **建议裁决选项**（用户定，不擅自改准则）：
  - A. 修订 §2.1③：「分栏按场景适配；信息密度低的简单应用（画图/模拟器/单画布类）允许单栏，须在卡内写明理由」；
  - B. 维持③，但新增「分栏质量验收」：分栏必须两侧皆有真实内容与独立交互，凑数式分栏（右栏空壳/纯装饰）不达标；
  - C. 双轨：简单应用白名单豁免 + 复杂应用维持硬门禁。
- **已受影响面**：现有为过门禁而做的双栏应用（台账 #228 扫描面）是否回改，随裁决一并定。
